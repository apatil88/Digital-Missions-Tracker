Purpose
Build one school application with a terminal coding agent, Claude Code or OpenAI Codex, through small, verifiable features. This pack defines a project-specific specification-driven process. No particular SDD framework or command-line toolkit is required.

What changes with a coding agent
The earlier platform supplied a scaffolded React project, a managed Supabase connection, hosting and a live browser preview. A coding agent supplies none of these. F00 now creates the repository structure, the D11 stack, a local Supabase environment and the test tooling. Hosting a demo is a separate, owner-approved step after release checks pass.
A coding agent can run commands, so evidence is real command output: migrations, lint, type checks, unit and database tests, and Playwright browser runs. Checks on a physical phone remain the owner's job.

Owner prerequisites
Node.js LTS, Git, Docker Desktop for the local Supabase stack, the Supabase CLI, and Claude Code or the Codex CLI. Local development needs no Supabase cloud project. A hosted demo needs a separate Supabase project holding fictional data only. Keep keys in .env.local. Never paste secret keys into an agent chat or commit them.

One-time setup
1. Read 03_DECISIONS.txt. Demo defaults authorize fictional-data behavior only. Resolve live-pilot gates before introducing real families.
2. Create an empty project folder and run git init. Copy this whole pack into the project as specs/ with file names unchanged.
3. Create the agent instruction files at the project root.
   AGENTS.md contains the full text of specs/01_PROJECT_KNOWLEDGE.txt. Codex reads AGENTS.md automatically at the start of each session.
   CLAUDE.md contains one line: @AGENTS.md. Claude Code reads CLAUDE.md automatically, and the @ line imports AGENTS.md, so both agents share one source.
   If 01_PROJECT_KNOWLEDGE.txt changes, edit it first and copy it to AGENTS.md again, so the two never drift.
4. Create the folder specs/reports/ for feature completion reports.
5. Commit this baseline before any application code exists.

Per-feature loop, for F00 and then each FR in build order
1. Start a fresh agent session. Claude Code: /clear or a new session. Codex: a new session. One feature per session keeps context focused on the right specification.
2. Create a feature branch, for example feature/FR01.
3. Plan. Claude Code: press Shift+Tab until plan mode is shown, then paste the feature's planning prompt. Codex: use read-only mode, or plan mode if your Codex version provides one, then paste the planning prompt. The prompt itself also forbids file changes, so it is safe in either tool.
4. Review the plan for requirement coverage, dependencies, migrations, row-level security policies, a test for each acceptance ID, and unresolved questions. Request revisions in the same session. Approve only the bounded feature scope.
5. Build. Leave plan or read-only mode, allow file edits and local commands, and paste the build instruction. Deny any command that targets a remote Supabase project, deploys, pushes, or touches real data.
6. Verify in a new session, so the verifier does not grade its own reasoning. Paste the verification prompt. Require actual evidence for each acceptance ID. Mark unavailable tests NOT RUN, never PASS. The agent writes the completion report to specs/reports/.
7. Review the diff and the completion report yourself, then commit and merge. Move to the next feature only after its blocking scenarios pass. If a prerequisite changes, rerun the affected downstream scenarios.

Using Claude Code and Codex together, optional
One agent builds and the other verifies. Both read the same AGENTS.md and specs, so the prompts work unchanged in either tool. Never let two agents edit the same branch at the same time.

[Unverified] Project specification v0.2. Proposed behavior pending the decisions in specs/03_DECISIONS.txt. This text is copied to AGENTS.md at the project root, and CLAUDE.md imports it.

Product
Digital III Missions Tracker for one martial arts school. Build a mobile-first PWA with a Supabase backend as proposed in the PRD, using a terminal coding agent. Use the D11 stack. Inspect the existing repository and integrations before adding libraries or generating migrations. Do not switch backend products without product-owner agreement.

Stack (D11, proposed)
React, TypeScript and Vite. Tailwind CSS with shadcn/ui components. React Router and TanStack Query. Supabase Postgres, Auth and row-level security. Transactional commands as Postgres functions called through Supabase RPC. Edge Functions only for privileged provider calls such as sending invitations. vite-plugin-pwa for the service worker. Vitest for unit tests, pgTAP through the Supabase CLI for database and policy tests, Playwright for browser tests.

Commands (created by F00, then kept stable)
npm run dev, npm run build, npm run lint, npm run typecheck, npm run test (Vitest), npm run test:db (supabase test db), npm run test:e2e (Playwright), npm run db:reset (local stack only: reruns migrations and the demo seed). supabase start and supabase stop control the local stack.

Users
Parent or guardian manages children. Adult student manages their adult profile. Both use family permissions. Instructor reviews school submissions. School administrator has instructor rights plus invitations, assignment, catalog enablement, cutoff configuration, and exceptions. A person might have family and staff memberships. Children have no login. One managing adult account per family for the pilot.

Scope
Teamwork is the first complete demonstration. Respect joins before the pilot. One school. Fictional data until live-pilot decisions are resolved. No payments, attendance, videos, child media, chat, leaderboards, native app-store release, AI suggestions, semantic AI matching, public registration, or multi-school management.

Domain rules
Exactly 50 active attested records per submission. Same or similar activity no more than twice within one assignment. Catalog variants share an activity group. Unmatched custom entries require instructor classification. Selecting a suggestion creates no credit. No bulk completion. No automatic attestation. Proposed adult self-attestation is gated for live use.

States
Persist not_started, in_progress, submitted, needs_changes, approved. Derive Ready to submit from submission validation only while in_progress. Needs changes stays visible until resubmission, with a separate ready indicator. Deadline openness is separate from mission state. Submitted and approved records are read-only for families. Administrator reopening creates needs_changes and records a reason.

Security and integrity
Enforce family ownership and staff permissions in the backend and database policies. Do not trust a browser-supplied role, actor, count, timestamp, attestation identity, or approval. Staff review never grants permission to rewrite family statements. Reject review and reopening of the actor's own family records. Use another reviewer.
Save submission content as immutable versions. Store review classifications separately from snapshot content. Use protected transactional commands, expected versions, and idempotency keys for mutations. Check the latest cutoff and record state inside submit. Require fresh authoritative confirmation before displaying success.
The Supabase service-role key is used only by server-side scripts, tests and Edge Functions. It never appears in browser code, in a VITE_ environment variable, in source control, or in the built app.

Deadlines
Administrator supplies a school timezone and exact cutoff. Two calendar days before graduation is a proposal requiring confirmation. A server-received submission at cutoff is permitted, after cutoff is rejected unless a valid extension applies. Open draft editing after cutoff does not permit submission. Late corrections need an administrator extension under the proposed default. Do not infer school timezone from the device.

Experience
Keep the student visible throughout logging and submission. Inter, primary #D94320, text #202124, background #FAF9F6, cards #FFFFFF, secondary #667085, approved #167347, warning #A66308, error #B42318. Proposed tokens, not verified official brand values. Rounded corners 8 to 12 pixels. Touch targets at least 44 CSS pixels. Support 360 CSS pixel screens. Keyboard access, visible focus, labels, accessible error summaries, and text alongside color.

PWA
Online-first. Cache the shell and public assets only. No authenticated student data in service-worker caches. No offline saves or queued submissions. Keep unsaved fields in current-page memory during retry and explain potential loss on page close. Clear in-memory records on logout. Installation is optional. No push or email reminder campaigns in this MVP.

Development process
Read the selected feature and shared contracts before editing. Preserve specs/ source documents. Implement one approved scope at a time. Keep logic in shared backend operations instead of duplicating rules across screens. Use acceptance IDs in test names. Test user behavior, unauthorized requests, and relevant concurrency failures. Do not treat a screenshot or mock data as evidence of backend correctness.
Report requirement coverage, actual test results, NOT RUN cases, migration changes, and gaps. Never describe unexecuted tests as passing. Do not publish or enable real participants as a side effect of completing a feature. Update specifications before changing approved behavior.

Agent operating rules
Work only on the feature named in the current prompt. Do not start the next feature.
Do not edit files in specs/ except completion reports in specs/reports/. Propose specification changes in your reply instead.
Use the local Supabase stack only. Do not run supabase link, supabase db push, a linked reset, a deployment, or any command against a remote project unless the owner asks for it in the current session.
Do not commit .env files, keys, tokens or test passwords. Keep variable names in .env.example without values.
Add schema changes as new files in supabase/migrations. Do not edit a migration that has already been merged.
Do not disable row-level security, loosen a policy, skip a test, or weaken an assertion to make a test pass.
Explain any new dependency outside D11 in the plan before installing it.
Do not push or merge. The owner reviews the diff.
Evidence means the command you ran and the result you observed.

[Unverified] Shared implementation contract v0.1. All names below are proposed logical contracts, not existing APIs. Map them to the inspected project and document the mapping. Preserve behavior if implementation names differ.

C01 Authentication and authority
Use authentication-provider user identifiers. school_memberships maps account to instructor or administrator rights. family_memberships maps one managing adult to a family for the pilot. students.family_id determines family scope. Staff also need family membership to edit their own family entries. Staff rights alone grant no family-write rights.
Administrators inherit reviewer rights. Parents and adult students are personas using family permission, not separate authentication systems. Reject all anonymous record reads. Deny access to another family's identifiers without leaking names, existence, counts, or errors containing protected data. Use NOT_FOUND for an unauthorized resource identifier and FORBIDDEN for a disallowed operation on an otherwise visible resource.
First administrator provisioning uses a trusted server-side setup step outside public registration. No role switcher, public admin signup, client-side role claims, or browser-held privileged keys. Self-service role escalation is forbidden.

C02 Data model minimum
All primary identifiers are UUIDs. Every school-owned record carries school_id or an unambiguous protected relationship. Use foreign keys, timestamps from the backend, and explicit active flags. Authorization follows relationships rather than user-submitted school identifiers.
schools: id, display_name, timezone, environment_mode demo/pilot, policy settings, version.
school_memberships: school_id, user_id, role instructor/admin, active. Unique school/user/role.
families: id, school_id, active.
family_memberships: family_id, user_id, owner=true, active. One active managing user per family in MVP.
students: id, family_id, display_name, age_band_id, kind child/adult, adult_user_id nullable, active, version. Adult profile maps to the managing adult. One own adult profile per family. Several child profiles allowed.
age_bands: id, school_id, label, catalog_key, active. School-configured labels, no full birth dates.
invitations: id, school_id, intended_role, invited_email, token_hash or provider reference, expires_at, accepted_by, accepted_at, revoked_at. Do not expose tokens in logs.
notice_acceptances: user_id, notice_version, accepted_at. Pilot notice content supplied before real use.
mission_templates: id, school_id, type teamwork/respect, version, approved_instructions, required_count=50, repeat_limit=2, enabled, approved_content flag. Version rather than overwrite instructions used by assignments.
activity_groups: id, template_type, stable grouping_key. Groups represent the same or similar action under school policy.
catalog_activities: id, school_id, template_type, activity_group_id, title, age_band_ids, setting, active, approved_content, version.
catalog_aliases: normalized_title, activity_group_id, template_type. Ambiguous aliases require review instead of automatic matching.
graduation_cycles: id, school_id, name, activity_start_date, activity_end_date, graduation_date, timezone, cutoff_at, archived_at, version. Dates use the configured school timezone, cutoff_at stores an absolute instant.
assignments: id, school_id, student_id, cycle_id, template_id, frozen_template_version/instructions/count/limit, state, content_version, lifecycle_version, current_submission_id. Unique student/template/cycle.
activity_records: id, assignment_id, source catalog/custom, catalog_id nullable, activity_group_id nullable, original_title, normalized_title, participation, completed_on, attestation_type parent/self, attested_by, attested_at, active, revision, created_at, updated_at.
submissions: id, assignment_id, sequence, submitted_at, submitted_by, source_content_version, frozen_student_display_name, frozen_mission_label, frozen_cycle_label, frozen_policy_metadata. Unique assignment/sequence.
submission_entries: submission_id, source_record_id, source_revision, ordinal, copied title/participation/date/catalog/group/attestation fields. Immutable to application roles after insert.
review_classifications: submission_id, source_record_id, review_group_key, reviewer_id, classified_at. Unique submission/entry. Does not modify the submitted statement.
review_decisions: id, submission_id, outcome approved/returned, reviewer_id, reason, flagged_entry_ids, decided_at. One final review decision per submission. Reopening does not erase an approval.
deadline_exceptions: id, assignment_id, expires_at, granted_by, granted_at, reason, revoked_at. At most one active exception per assignment. Updating an exception revokes the old row and creates a new row in one transaction.
audit_events: actor_id, action, entity_id, entity_version, occurred_at, structured change references. Append-only, school-scoped. Full student narratives remain in protected records, not analytics logs.
mutation_receipts: actor_id, operation_name, request_id, payload_hash, outcome_reference, created_at. Unique actor/operation/request_id. Receipt retention is an operational decision, not a school mission policy.

C03 State and status
Family editable states: not_started, in_progress, needs_changes. Saving the first record changes not_started to in_progress. Removing the last record changes in_progress to not_started. Removing all returned records preserves needs_changes so feedback is not hidden.
Ready to submit is a derived label only for in_progress with zero submission blockers. needs_changes retains its label and shows Resubmit enabled when validation passes. Draft editing remains permitted after the submission cutoff if the cycle is not archived.
submit changes an editable assignment to submitted. return changes submitted to needs_changes. approve changes submitted to approved. reopen changes approved to needs_changes and records an administrator reason. No direct family transition to approved. An archived cycle is read-only, including review mutations. Archive requires every existing assignment to be approved, or no assignments. An administrator restores the cycle before reopening an approval. Restore preserves all assignment states and history, changes only archive status, and records an audit event.
Deadline openness is computed separately. A submitted mission stays submitted after cutoff. Overall graduation eligibility is outside this application.

C04 Mutation and error envelope
All mutations require an authenticated actor, operation-specific input, request_id, and expected version where the operation updates existing mutable data. Resolve actor and ownership server-side. Return {ok, data, error}, where error has code, safe message, field_errors, and retryable. Do not place student narratives in error telemetry.
Common errors: UNAUTHENTICATED, FORBIDDEN, NOT_FOUND, VALIDATION_FAILED, VERSION_CONFLICT, INVALID_STATE, DUPLICATE_REQUEST_PAYLOAD, POLICY_NOT_CONFIGURED, RATE_LIMITED, TEMPORARILY_UNAVAILABLE.
Scope idempotency to actor + operation + request_id. Same key and payload returns the original committed result even after the state changes. Same key and different payload returns DUPLICATE_REQUEST_PAYLOAD. Check current access before returning a previous receipt. Pending writes must not emit success. After an ambiguous timeout, retry with the same key.
Use a consistent transaction locking order. Serialize commands affecting one assignment. Recheck related settings inside the transaction. Saving, editing, deleting, submitting, classifying, approving, returning, and reopening must not partially commit. Record audit events in the same transaction as the action where feasible. If an external auth/email step is involved, use an explicit pending/failed status and retry rather than pretending the external operation committed atomically.

C05 Versions and snapshots
content_version increments on every activity add/edit/remove. lifecycle_version increments on state, review classification, and exception changes affecting the assignment. Submission stores the current content version. Review commands require current submission ID and expected lifecycle version. A setting version captures cutoff changes.
Submission content is append-only. Corrections edit working records, then create a new submission sequence. Approval applies only to current_submission_id. Review classification is an overlay for one submission. Reset custom review classification on each new submission, even if text is unchanged, as a proposed MVP simplification. Known catalog groups remain available from the snapshot. No retroactive catalog edits change snapshots.
Families see their own working records, submissions, decisions, and feedback. Full staff audit metadata is admin-scoped. Staff review never allows editing a parent's words or attestation.

C06 Counts and repetition
Count active records within one assignment. Maximum 50 on create, exactly 50 on submit. Edit excludes the record being edited from usage counts. Removal frees one occurrence.
Normalize titles: Unicode NFKC, lowercase with one consistent locale-independent rule, replace punctuation with spaces, collapse whitespace, trim. Reject an empty result. Preserve original text. Use identical server normalization in all commands, never a browser-only approximation as authority.
Known catalog variants and unambiguous aliases map to one stable group. Count catalog entries plus custom aliases together. Unmatched custom titles use a provisional normalized-title key for exact repetition checks. Two accepted occurrences per group, third rejected. Similar wording without a known mapping remains unclassified.
Review grouping combines catalog group identities with instructor-assigned group keys. A reviewer merges equivalent custom groups where needed. Approval checks grouped totals <=2 and zero unresolved custom classifications. Catalog selection does not prove the described action matches the suggestion. Return misleading or unclear records rather than altering statements.

C07 Dates and deadlines
completed_on is a date, not an event timestamp. Require cycle start <= completed_on <= min(cycle end, school-local today). Logging a past date retains the actual attestation and creation timestamps. Editing the participation, title, source, classification, or date requires renewed attestation.
effective_cutoff=max(cycle cutoff, unrevoked assignment exception expiry). Evaluate using server time at the authoritative transactional validation point. A request arriving earlier but validated after expiry fails. UI is a guide, not authority. Same-key retries of an already committed submission return its receipt after expiry.
Administrator explicitly configures timezone and local cutoff date/time. Reject nonexistent local times at daylight-saving transitions. Require an explicit offset choice for ambiguous local times. Preview the absolute instant before saving. Graduation date changes never silently alter cutoff. Show existing cutoff and require explicit confirmation.
An extension changes submission timing only, not the permitted activity window. Corrections involving new activity dates require those dates to remain inside the activity window. Post-assignment activity-window edits need a separate approved policy change, not an implicit extension.

C08 Input and UI defaults proposed for demo
Display name: trimmed 1 to 60 characters. Activity title: 3 to 120 characters. Participation: 10 to 500 characters, with a separate explanation field even when a catalog title exists. Reason/feedback: 10 to 1000 characters. These length limits do not prove truthfulness. Treat entries as plain text, escape on display, and reject empty or control-only strings. Limits are proposed implementation defaults in D02.
Keep selected student, mission, progress and cutoff visible. Loading state, empty state, permission error, offline state, validation errors, retry, and stale-version refresh are required. Use an accessible error summary and field errors. Do not wipe unsaved text on a rejected save. Re-authentication must not automatically attest or submit.
Cache no authenticated API responses in the service worker. Do not store child narratives in browser persistent storage. Temporary form content lives only in page memory. Browser close and mobile process termination might discard memory, so explain this limit and use navigation protection where supported.

C09 Read contracts
get_family_dashboard(): own students and assignments, recorded_count, state/display_status, blocking_count, unresolved_custom_count, effective_cutoff, next_action. FR03 owns presentation.
get_mission_detail(assignment_id): authorized working records, feedback, latest submission metadata, validation summary, permissions. Returns server time and versions.
get_review_queue(cycle_id,filters,cursor): authorized school records, paginated. Server-enforced school scope.
get_submission(submission_id): immutable entries plus current review overlay and allowed actions.
get_school_status(cycle_id,filters,cursor): roster and all required assignments with aggregate mission status. Students without assignments remain visible.
get_print_record(assignment_id,submission_id optional): protected view model from working draft or selected immutable submission.
Read routes never imply write permission. All list queries are scoped on the server before pagination or aggregation.

C10 Command ownership
FR01: invite_account, accept_invitation, save_student_profile.
FR02: create_cycle, update_cycle, assign_mission, set_catalog_enabled, archive_cycle, restore_cycle. Cutoff calculation delegated to FR10.
FR04: list_suggestions and selection UI only. Catalog seed/import is foundation/setup.
FR05: create_activity.
FR06: update_activity, remove_activity.
FR07: normalize_activity_title, resolve_activity_group, validate_repetition. These are internal services, not privileged user endpoints.
FR08: validate_submission internal service plus authorized preflight read operation.
FR09: submit_mission.
FR10: resolve_cutoff, set_cycle_cutoff, grant_extension, revoke_extension.
FR12: classify_entry, merge_review_groups, approve_submission, return_submission, reopen_approval. Owns transactional review mutations.
FR11: review UI calling FR12 commands. Do not implement another approval path.
FR13/FR14/FR15: authorized read models, print, and computed notices. FR15 also owns admin-only set_reminder_thresholds using the common mutation envelope. No alternate mission mutations to bypass existing commands.

C11 Completion gate
Feature completion requires acceptance evidence and authorization checks, including direct backend attempts. UI-only hiding is insufficient. Use unit tests for pure rules, integration tests for transactional commands and permissions, and browser checks for user flows. Run additional regression only for affected shared behavior. Test fixtures stay fictional and outside production seed paths.
All listed acceptance scenarios are requirements, not evidence of executed tests. Deployment, real onboarding, and privacy-policy approval are outside feature completion.

[Unverified] Decision register v0.2. No school approval is implied. v0.2 replaces the earlier build platform with a terminal coding agent and adds D11.

Confirmed product direction from your instructions
One school. One mission-tracking problem. One working application. Build with a terminal coding agent, Claude Code or Codex, for a founder pitch. The PRD supplies the 15 feature identifiers and the initial scope.

Proposed implementation defaults
D01 One managing adult per family. Parent and adult student share family access, with separate profiles. First admin provisioned through trusted setup. Pilot rights changes handled by the administrator or a controlled support process, without a full role-management product.
D02 Input limits in C08, seven-day invitation expiry, school-configured age-band labels, and a fixed English MVP interface. Invitation expiry is an implementation proposal, separate from mission cutoffs.
D03 needs_changes remains visible until resubmission. An empty returned mission stays needs_changes. Ready to submit is derived only for in_progress.
D04 New submission requires fresh custom-activity classification. Review overlays do not mutate historical content. This trades some review effort for simpler version handling.
D05 At most one active extension per assignment. A replacement records both revocation and new grant. Extensions do not widen the activity date window.
D06 Exact cutoff inclusion uses server time at transaction validation, with equality accepted. Same-key retry after a committed submission returns the earlier receipt.
D07 Family draft edits remain allowed after cutoff. Archive requires all existing assignments approved, or no assignments. Archived cycles reject edits and review mutations but allow historical reads and printing. Admin restore_cycle records an audit event and preserves assignment states. Restore precedes reopening an archived approval. This is a proposed clarification beyond the original PRD's brief archive requirement.
D08 An administrator and instructor are both forbidden from reviewing or reopening their own family's submission. Another authorized staff member handles the case.
D09 Deadline notices are computed on read, use the effective cutoff, and use configurable 7-day and 1-day thresholds. No dismissal persistence or push subscription in the MVP.
D10 Course content is imported through a controlled seed path. Simple enable/disable controls are included. A full catalog editor and historical record migration are excluded.
D11 Build stack and environments, replacing the earlier platform-managed project. React, TypeScript and Vite. Tailwind CSS with shadcn/ui. React Router and TanStack Query. Supabase Postgres, Auth and row-level security, keeping the PRD backend. Transactional commands as Postgres functions. Edge Functions only for privileged provider calls. vite-plugin-pwa. Vitest, pgTAP through the Supabase CLI, and Playwright. Development and all automated tests run against a local Supabase stack. A hosted demo uses a separate Supabase project holding fictional data and a static host chosen by the owner. Deployment is outside feature completion. The F00 plan may propose substitutes with reasons, and the owner approves them before code.

Founder decisions required before a live pilot
P01 Permission to digitize curriculum, use proposed product branding, and provide activity suggestions. Demo uses clearly labeled sample content. Pilot catalog remains disabled without approved content.
P02 Acceptance of digital submission and printable records. Keep the accepted paper workflow authoritative until confirmed.
P03 School timezone, exact cutoff time, two-calendar-day interpretation, correction after cutoff policy, and exception authority. Demo uses a clearly fictional configured timezone and date. No production cutoff is inferred.
P04 Activity-window dates, grouping of similar actions, same-day repetitions, and cross-mission credit. Demo permits two separate occurrences in one group, even on one date, with separate records. Do not copy one occurrence across assignments.
P05 Adult self-attestation. Demo permits fictional adult examples. Pilot adult logging stays disabled until accepted or an alternate verifier is specified.
P06 Privacy notice, parental authorization, retention, deletion, backup handling, support owner, hosting owner, and application/curriculum ownership. No legal compliance claim.
P07 Staff roster and second reviewer for staff families. A single reviewer pilot must exclude that reviewer's own family or nominate another reviewer.

Implementation gates
Build fictional-data features with the stated demo defaults. Do not invent founder approval dates, retention periods, a school's timezone, or a consent document. For pilot activation, require an operational signoff record naming the responsible person and resolved P01 to P07 decisions. A full compliance administration screen is outside this MVP.
Policy changes affecting existing assignments require an explicit change plan and migration test. Changing a setting must not rewrite historical submissions. If a real requirement conflicts with this pack, update the decision register and feature version before implementation.

4 User workflow and screens

Return usage and any matching entries. For unknown wording, use a provisional exact-title key and mark classification pending. During review, evaluate snapshot entries plus the review overlay to detect semantic grouping conflicts.

5 Functional requirements
FR07-R01 Implement C06 normalization as one backend function with deterministic tests. Preserve original text. Do not accept browser-provided normalized text as authoritative.

FR07-R02 Resolve catalog variants and unambiguous aliases to a common group. Unknown or ambiguous aliases use provisional normalized-title grouping and pending classification.

FR07-R03 Allow at most two active occurrences of a known or provisional exact-title group. Restrict counts to one assignment, never across siblings or cycles. A third matching occurrence blocks create/edit and submission.

FR07-R04 Return matching record IDs only after ownership authorization. Do not reveal another student's entries through validation errors.

FR07-R05 Expose pure review evaluation over snapshot plus classification overlay. Each unresolved custom entry blocks approval. Merge equivalent review groups before counting final occurrences.

FR07-R06 Normalization does not establish semantic uniqueness. No model-generated similarity verdict. Instructor classification writes belong to FR12. Preserve review findings without rewriting attested text.

6 Data and logical operation contracts
normalize_activity_title(title) -> normalized_title.
resolve_activity_group(template_type, source, catalog_id/title) -> known_group_id optional, provisional_key optional, classification_required.
validate_repetition(assignment_id, candidate, excluding_record_id optional) -> allowed, usage, matching_record_ids, classification_required.
evaluate_review_groups(submission_entries, classifications) -> unresolved_entry_ids, over_limit_groups, grouped_counts.
Internal services require authorized calling commands or scoped reads. No open endpoint listing arbitrary group membership.
Logical names are proposed. Map to actual inspected backend operations and preserve behavior. All reads and writes inherit C01 and C04. All UI states inherit C08.

7 Errors and recovery
REPEAT_LIMIT includes authorized matching records and remaining allowance. EMPTY_NORMALIZED_TITLE, AMBIGUOUS_ALIAS as classification flag, plus standard validation errors. Unknown similarity is not a hard save rejection.

FR07-AC01 Given titles differing by case, punctuation or repeated spaces, when normalized, then equivalent fixture titles share a provisional key.

FR07-AC02 Given two catalog variants or known custom aliases in one group, when adding a third, then validation rejects the addition.
