1 Outcome
A family sees the correct student, recorded progress, deadline and next action without confusing attestation with approval.

2 Context required for the coding agent
Read 01_PROJECT_KNOWLEDGE.txt, 02_SHARED_CONTRACTS.txt, 03_DECISIONS.txt and 05_TEST_FIXTURES.txt with this specification. This file is not a substitute for the shared authorization, date, version and state rules.
Dependencies: FR01, FR02, FR08, FR10. Implemented prerequisites must have acceptance evidence. If a prerequisite is absent, report the exact missing dependency. Do not silently fake backend behavior.

3 Users and permissions
Parent: select a child and open assigned missions.
Adult student: select own adult profile in the same family selector.
Instructor: school status belongs to FR13, family editing requires own family membership.
Administrator: same scope separation as instructor.

4 User workflow and screens
Open /family. Load authorized profiles, select a profile, then load mission cards. Each card shows mission name, recorded count out of 50, state, cutoff, issue count and next action. Open a card for mission detail. Switching students cancels or ignores old requests so results from the previous student do not overwrite the selected view.

5 Functional requirements
FR03-R01 Display only assigned missions belonging to the selected profile. Show distinct states for no profiles, no assignments, no records, loading, unavailable and access denied.

FR03-R02 Compute counts from active records. Label progress Recorded activities. Parent-attested and self-attested are distinct from instructor Approved.

FR03-R03 Use C03 states and FR08 validation. In progress with 50 records and no blockers shows Ready to submit. Needs changes remains visible with Resubmit when eligible.

FR03-R04 Display explicit school-local cutoff and timezone, plus open/closed status from FR10. A deadline closing does not remove submitted or approved status.

FR03-R05 Next actions: Add activity below 50 in editable state, Review submission when ready, View feedback when returned, View submission when submitted, View approval when approved. An expired cutoff explains blocked submission while retaining permitted edits.

FR03-R06 Refresh after a successful mutation, on return to the app, and when the cutoff boundary is reached. Use authoritative reads, loading indicators and retry rather than fabricated counts or stale success.

6 Data and logical operation contracts
get_family_dashboard() -> students[], assignments[], recorded_count, display_status, effective_cutoff, blocking_count, unresolved_custom_count, next_action.
get_mission_detail(assignment_id) -> records, feedback, permissions, validation and versions.
No dashboard-specific mutation. All actions delegate to the owning feature command. Selected student stays in page state and route context, not a source of authorization.
Logical names are proposed. Map to actual inspected backend operations and preserve behavior. All reads and writes inherit C01 and C04. All UI states inherit C08.

7 Errors and recovery
UNAUTHENTICATED prompts sign-in, NOT_FOUND hides unauthorized identifiers, TEMPORARILY_UNAVAILABLE shows retry. Old-profile responses are ignored after selection changes.

8 Acceptance scenarios
FR03-AC01 Given FAMILY_A with two children and an adult profile, when switching profiles, then cards, counts and next actions all match the selected profile.

FR03-AC02 Given slow responses for two profile selections, when the older response arrives last, then the latest selected profile remains displayed.

FR03-AC03 Given M0, M49, M50, M_RETURNED and M_APPROVED, when opening each, then count, status and action match C03 and FR08.

FR03-AC04 Given a submitted mission after cutoff, when refreshing, then status remains Submitted and editing stays disabled.

FR03-AC05 Given FAMILY_B using a FAMILY_A mission URL, when loading detail, then no protected record, count or name appears.

FR03-AC06 Given an unavailable backend, when opening the dashboard, then no zero-count success substitute appears and retry is available.
These scenarios are specified, not executed. Test actual behavior and backend authorization. Record PASS, FAIL or NOT RUN with evidence for every identifier.
